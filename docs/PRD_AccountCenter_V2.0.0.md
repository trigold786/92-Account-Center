## 1. 产品概述

### 1.1 产品定位与目标

Account Center（账户管理微服务）是 Neuro 产品线的核心基础设施，承担统一认证、五级身份体系、积分经济、推荐返利、订阅生命周期、RFM 用户画像及合规审计等完整商业闭环。

V1.3.1 已完成全量交付，具备以下能力：

- 8 个 Go 微服务 + 4 端前端（Web/微信小程序/iOS/Android）完整架构
- 51 个 PRD 需求 + 8 个额外功能全部实现
- MLPS 3.0 等保三级合规、SM3/SM4 国密、PII 脱敏中间件、审计日志哈希链
- Docker 全容器化部署、VictoriaMetrics 监控、130+ 配置项驱动运营

V2.0 的核心目标：

1. **商业化上线就绪** — 补齐支付集成、账号注销执行、网关超时等生产级短板
2. **合规红线解除** — 落实账号注销 Worker、密码哈希升级至 argon2id、分布式追踪接入
3. **体验竞争力提升** — 提升测试覆盖率、统一文档体系、构建 K8s 生产级编排

基于 ITERATION V1.0.1 逐行审查，共识别 **77 项改进建议**，按优先级分布：

| 优先级 | 数量 | 定位 |
|--------|------|------|
| P0 | 14 | 上线阻断项，必须在 V2.0 完成 |
| P1 | 30 | 体验与增长关键项，V2.1 迭代 |
| P2 | 29 | 竞争力提升项，V2.2 迭代 |
| P3 | 4 | 长期规划项，V2.3 迭代 |

### 1.3 V2.0 迭代目标

基于 ITERATION V1.0.1 识别的 **8 项已知短板**，作为 V2.0 系列迭代的驱动目标：

1. **测试覆盖率低** — Go 测试文件仅 16/167（~9.6%），5 个服务仅有冒烟测试
2. **文档不一致** — README、ARCHITECTURE.md 与 SSD 之间端口/服务描述存在偏差
3. **密码哈希方案弱** — 使用 SM3+salt（经代码验证确认）而非 bcrypt/argon2，暴力破解防护较弱
4. **无分布式追踪** — 缺少 OpenTelemetry/Jaeger，跨服务问题定位困难
5. **无 K8s 部署** — 仅有 Docker Compose，缺少 Helm/K8s 生产级编排
6. **无真实支付集成** — 订阅购买流程完整但未对接真实支付网关
7. **账号注销未实际执行** — 系统记录注销请求但无后台 Worker 执行数据删除/匿名化（合规红线）
8. **网关无请求超时** — API Gateway 反向代理无 Transport 超时，后端卡死可拖垮全局

**分阶段交付策略**：

| 阶段 | 优先级 | 目标 | 版本 |

| Phase 6 | P0（14 项） | 上线准备冲刺 | V2.0 |

## 3. 功能需求

### 3.0 概述

本节按迭代 Phase 分组列出全部功能需求。需求 ID 沿用 ITERATION V1.0.1 编号，保持可追溯性。

每项需求包含：
- **需求 ID**: 与 ITERATION 对应的唯一编号
- **名称**: 简明描述
- **优先级**: P0/P1/P2/P3
- **维度**: 合规/安全/可靠性/质量/运维/商业化/UX/功能
- **用户故事**: 作为…我希望…以便…
- **验收标准**: 可量化的完成条件（至少 3 条）
- **依赖**: 前置需求或外部依赖

### 3.1 Phase 6 — P0 需求（阻塞上线，共 14 项）

> 以下 14 项为系统上线前必须完成的阻塞项，涵盖合规、安全、可靠性、质量、运维、商业化、UX 与功能维度。

#### NF-01: 账号注销 Worker 实现

**优先级**: P0  
**维度**: 合规  
**用户故事**: 作为用户，我希望提交账号注销请求后，系统在 7 天冻结期结束后自动删除或匿名化我的个人数据，以便我的隐私权利得到法律保障（PIPL/MLPS 合规）。  
**验收标准**:
- [ ] 用户在 7 天冻结期内可随时撤回注销请求，撤回后账号恢复正常可用状态
- [ ] 冻结期到期后，Worker（Asynq 定时任务）自动将手机号、邮箱、姓名等 PII 字段替换为 `deleted_xxx` 格式
- [ ] `DeletionDeletedAt` 字段在匿名化执行后被正确写入当前时间戳
- [ ] Worker 同时清理 Redis 中该用户的 session 和缓存数据，并写入审计日志记录完整注销流程
**依赖**: 无

#### NF-02: 网关请求超时配置

**优先级**: P0  
**维度**: 可靠性  
**用户故事**: 作为系统运维人员，我希望 API 网关对所有后端请求配置合理的超时时间，以便后端服务卡死时网关不会无限挂起导致整个系统不可用。  
**验收标准**:
- [ ] `httputil.ReverseProxy` 的 Transport 配置 `ResponseHeaderTimeout: 30s`
- [ ] `httputil.ReverseProxy` 的 Transport 配置 `IdleConnTimeout: 90s`
- [ ] 全局请求超时中间件设置最大请求时间为 60s
- [ ] 超时请求返回 HTTP 504 状态码及标准错误响应体，不产生连接泄漏
**依赖**: 无

#### AR-13: 密码哈希升级至 argon2id

**优先级**: P0  
**维度**: 安全  
**用户故事**: 作为安全管理员，我希望系统使用 industry-standard 的 argon2id 算法存储密码，以便用户密码具备更强的抗暴力破解能力。  
**验收标准**:
- [ ] 新用户注册和修改密码时使用 argon2id 算法进行哈希存储
- [ ] 存量 SM3 哈希用户在下次成功登录时自动触发 rehash，密码以 argon2id 重新存储
- [ ] SM3 哈希保留用于审计完整性校验，不删除历史记录
- [ ] 过渡期内密码验证同时兼容 SM3 和 argon2id，无用户感知中断
**依赖**: 无
