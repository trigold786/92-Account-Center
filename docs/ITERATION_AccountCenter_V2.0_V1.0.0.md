## 1. 项目现状总览与评价

### 1.1 项目概况

Account Center（账户管理微服务）是 Neuro 产品线的核心基础设施，已完成 V1.3.1 版本全量交付。系统采用 **8 个 Go 微服务 + 4 端前端**（Web/微信小程序/iOS/Android）架构，覆盖统一认证、五级身份体系、积分经济、推荐返利、订阅生命周期、RFM 用户画像、合规审计等完整商业闭环。

### 1.2 已实现成果

| 维度 | 成果 | 自评 |
|------|------|------|
| 后端服务 | 8 个微服务，167 个 Go 源文件，51 个 PRD 需求 + 8 个额外功能全部实现 | 100% |
| 前端覆盖 | Web（Vue 3）、微信小程序、iOS（SwiftUI）、Android（Compose）四端齐备 | 100% |
| 安全合规 | MLPS 3.0、SM3/SM4 国密、PII 脱敏中间件、审计日志哈希链 | 完整 |
| 运维体系 | Docker 全容器化、VictoriaMetrics 监控、配置管理中心 | 基础完整 |
| 文档体系 | BRD、PRD、SSD、架构文档、API 规范、部署指南、移动端适配报告 | 丰富 |

### 1.3 核心优势

1. **架构完整性高**：从网关到业务服务到数据产品，形成完整闭环
2. **安全合规扎实**：SM3/SM4 全链路国密、审计日志 SM3 哈希链、PII 自动脱敏
3. **配置驱动运营**：130+ 配置项 + 发布审批流程，支持无代码调参
4. **跨平台一致性**：四端统一的暗色科技风设计语言
5. **抗风险能力**：熔断器、限流、优雅降级、Redis 故障回退

### 1.4 已知短板

1. **测试覆盖率低**：Go 测试文件仅 16/167（~9.6%），5 个服务仅有冒烟测试
2. **文档不一致**：README、ARCHITECTURE.md 与 SSD 之间端口/服务描述存在偏差
3. **密码哈希方案弱**：使用 SM3+salt（经代码验证确认）而非 bcrypt/argon2，暴力破解防护较弱
4. **无分布式追踪**：缺少 OpenTelemetry/Jaeger，跨服务问题定位困难
5. **无 K8s 部署**：仅有 Docker Compose，缺少 Helm/K8s 生产级编排
6. **无真实支付集成**：订阅购买流程完整但未对接真实支付网关
7. **账号注销未实际执行**：系统记录注销请求但无后台 Worker 执行数据删除/匿名化（合规红线）
8. **网关无请求超时**：API Gateway 反向代理无 Transport 超时，后端卡死可拖垮全局

## 2. 用户体验（UX）维度分析

### 2.1 登录/注册旅程

**现状**：统一输入框自动识别手机/邮箱/账号 ID，首次注册须用手机号。支持短信验证码、Magic Link 邮件登录。

| # | 改进项 | 现状问题 | 建议方案 | 优先级 |
|---|--------|----------|----------|--------|
| UX-01 | 一键登录/注册 | 当前仅支持手机号+验证码，步骤较多 | 接入微信一键登录（小程序已有基础）、Apple Sign-In（iOS）、Google One Tap（Android），减少注册流失 | P1 |
| UX-02 | 生物识别快捷登录 | auth-service 已实现生物识别 API，但客户端未对接 | iOS Face ID/Touch ID、Android 指纹识别对接已有后端接口，优先实现"记住设备+生物识别免密" | P1 |
| UX-03 | 短信验证码自动填充 | 移动端适配报告标记为低优先级 | iOS SMS Code AutoFill、Android SMS Retriever API 可大幅减少用户操作，建议提升至 P1 | P2 |
| UX-04 | 渐进式注册 | 首次必须手机号，门槛较高 | 支持"游客浏览→兴趣触发→邮箱注册→手机验证"的渐进漏斗，降低首次接触摩擦 | P2 |

### 2.2 首页/仪表盘体验

**现状**：Dashboard 展示 RFM 评分、积分余额、订阅状态、用户等级和快捷入口。

| # | 改进项 | 现状问题 | 建议方案 | 优先级 |
|---|--------|----------|----------|--------|
| UX-05 | 个性化仪表盘 | 所有用户看到相同布局 | 根据用户等级（L0-L4）动态调整卡片优先级：L0 突出升级引导，L2+ 突出积分和权益使用，L4 突出专属服务入口 | P1 |
| UX-06 | 空状态引导 | 未评估空状态体验 | 新用户首次进入时积分为 0、无订阅、无推荐，应设计友好的空状态引导（如"邀请好友赚积分"引导卡片） | P2 |
| UX-07 | 搜索/快捷操作 | 无全局搜索 | 添加全局搜索或快捷操作面板，高频操作（充值、查积分、改密码）一键触达 | P3 |

### 2.3 订阅/付费旅程

**现状**：支持购买、续费、升降级、过期降级完整生命周期，积分可抵扣。

## 3. 功能完整性维度分析

### 3.1 支付与交易体系

**现状**：订阅购买/升降级 API 完整，积分抵扣计算逻辑完备，但未对接真实支付。

| # | 功能缺口 | 影响范围 | 建议方案 | 优先级 |

| FN-02 | 订单管理系统 | 无独立订单表 | 新建 `orders` 表，记录支付流水、状态机（待付→已付→已取消→已退款），支持订单查询/导出 | P0 |

### 4.5 移动端广告变现策略

#### 4.5.1 广告策略设计原则

- **付费用户（L2-L4）零广告**，作为付费核心价值主张
- **免费用户（L0-L1）分级接触广告**，L0 接触频率高于 L1
- **不做奖励积分广告**，避免积分通胀和作弊风险
- 广告形式精简，仅保留**开屏广告**和 **Banner 广告**两种
- 视频广告（如有）严格限制**最长 5 秒**
- 每平台 **2 个 SDK，一主一备**，管理端可一键切换

#### 4.5.2 广告位与等级政策

| 广告位 | 展示场景 | L0（注册未实名） | L1（实名免费） | L2-L4（付费） | 时长/规格 |
|--------|----------|-----------------|---------------|--------------|-----------|
| 开屏广告 | App 冷启动 | 每次冷启动展示 | 每日首次冷启动 | 无 | 图片/视频，视频≤5秒，2秒可跳过 |

| 维度 | Dev | UAT | Prod |
|------|-----|-----|------|

| Redis 部署 | Docker 单容器 | **ECS 本地部署**（单节点 AOF 持久化，多项目共享） | Redis Sentinel (3 节点) 或 Cluster |

> - 上表所有技术的**二进制版本/镜像 tag 必须完全一致**。Dev 环境不运行 Kafka 但兼容层（Redis Streams）确保代码逻辑与 Prod Kafka 消费者/生产者接口一致。

> - **Dev 环境必须配置完整的监控和日志栈**：使用 Docker Compose 容器化部署 VictoriaMetrics + Promtail + Loki + Grafana，确保开发阶段即可发现性能和日志问题，与 UAT/Prod 保持一致的可观测性体验。

##### 回滚策略

| 场景 | 触发条件 | 回滚方式 | 预计时间 |
|------|---------|---------|---------|
| 应用层回滚 | 金丝雀阶段错误率 > 0.5% | `helm rollback` / `kubectl rollout undo` | < 2 分钟 |
| 数据库回滚 | Migration 引起数据问题 | `goose down` 回滚至上一版本 | < 5 分钟 |
| 配置回滚 | config-service 发布异常 | config-management-ui "回退到上一版本" | < 1 分钟 |
| 全量回滚 | 严重故障 | DNS 切换旧集群 + PG 时间点恢复 | < 30 分钟 |

### 5.9 版本锁定策略

1. **Go 服务**：`go.mod` 中所有依赖使用精确版本（`vX.Y.Z`）
2. **前端**：`package.json` 使用精确版本或 `~X.Y.Z`（补丁级更新）
3. **Docker 镜像**：docker-compose.yml 使用精确 tag（如 `postgres:18.2` 而非 `postgres:latest`）
4. **CI 门禁**：定期（每月）检查依赖更新，通过 `go list -u -m all` / `npm outdated` / Dependabot 自动化

## 6. 代码级深潜补充发现

> 以下问题通过对实际代码的逐行审查发现，超出文档层面的分析。

| # | 新发现问题 | 严重程度 | 详细说明 | 建议方案 | 优先级 |
|---|-----------|---------|---------|----------|--------|
| NF-01 | 账号注销未实际执行 | 🔴 高/合规 | `account-service` 记录注销请求和 7 天冻结期，但**无后台 Worker/Cron 执行实际数据删除或匿名化**。`DeletionDeletedAt` 字段定义但从未被写入。用户以为数据已删除，实际全部保留。严重违反 PIPL/MLPS。 | 实现 `deletion-worker`（Asynq 定时任务）：冻结期到期后自动匿名化用户数据（手机/邮箱/姓名替换为 `deleted_xxx`）、删除敏感字段、写入 `DeletionDeletedAt`。需同时清理 Redis session/cache。 | P0 |
| NF-02 | 网关无请求超时 | 🔴 高/可靠性 | `api-gateway` 反向代理使用默认 `httputil.ReverseProxy`，**无 Transport 级别超时配置**。后端服务卡死可导致网关连接无限挂起，拖垮整个系统。 | 为 `httputil.ReverseProxy` 的 Transport 配置 `ResponseHeaderTimeout: 30s`、`IdleConnTimeout: 90s`；添加全局请求超时中间件（如 60s）。 | P0 |
| NF-03 | 服务间无熔断器 | 🟡 中/可靠性 | 熔断器仅存在于 SMS 外部供应商。服务间 HTTP 调用（account→credit, account→notification, gateway→所有后端）**无熔断保护**。任一下游服务故障可引发级联失败。 | 将 `notification-service/pkg/circuitbreaker` 提升为 `pkg/circuitbreaker` 共享包，为所有服务间 HTTP 客户端添加熔断器（阈值 5 次/30s 恢复，与 SMS 熔断策略一致）。 | P1 |
| NF-04 | 健康检查为假健康 | 🟡 中/运维 | 所有服务 `/health` 仅返回 `{"status":"ok"}`，**不检查 DB/Redis 连通性**。服务可返回健康但实际无法处理请求。K8s/Docker 无法检测真实故障。 | `/health` 端点增加真实依赖检查：`SELECT 1`（PG）、`PING`（Redis）、可达性检查（依赖服务）；检查失败返回 503 + 详细状态。 | P1 |
| NF-05 | 配置无热更新 | 🟡 低/运维 | config-service 支持动态修改，但其他服务**仅在启动时加载一次**（`pkg/config/client.go` 为单次 HTTP GET）。配置变更需重启所有服务，削弱配置中心价值。 | 方案一：定时轮询（每 30s 从 config-service 刷新配置，内存覆盖）；方案二：Redis Pub/Sub 推送通知；方案三：服务端发送 Server-Sent Events。推荐方案一，实现最简。 | P2 |
| NF-06 | 移动端无深度链接 | 🟢 低/增长 | iOS/Android 均未配置 Universal Links/App Links，无 `apple-app-site-association` / `assetlinks.json`。无法通过链接直接打开 App 特定页面（推荐链接跳转、订阅页深度链接）。 | iOS: 添加 `com.apple.developer.associated-domains` + 托管 AASA 文件；Android: 添加 `<intent-filter>` + `assetlinks.json`；支持 `neuro://` 自定义 scheme。 | P2 |
| NF-07 | API Gateway 代码单文件 | 🟢 低/代码质量 | 网关 461 行全在 `cmd/main.go`，包含 JWT/限流/CORS/脱敏/代理全部逻辑，维护性差。 | 拆分为 `internal/middleware/`（jwt.go、ratelimit.go、cors.go、desensitize.go）+ `internal/proxy/`（reverse_proxy.go）+ `cmd/main.go`（仅路由注册和启动）。 | P2 |
