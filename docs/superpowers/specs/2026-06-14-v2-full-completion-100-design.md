# Account Center V2.0 全量需求完成度 100% 提升设计

> 文档类型：设计规格
> 版本：V0.1.0
> 日期：2026-06-14
> 范围：PRD V2.0.0 全部 86 项需求（P0/P1/P2/P3）
> 实施模式：Phase 顺序交付 + 业务闭环实施
> 状态：待评审

## 1. 目标与范围

本设计用于将 Account Center V2.0 从“文档声称完成、局部代码实现”的状态，提升为“BRD/PRD/SSD/UAT 可追溯、代码真实落地、业务闭环完整、测试证据充分”的 100% 完成状态。

目标：
- PRD V2.0.0 中 86 项需求全部真实完成。
- 每项需求具备证据链：后端代码、端侧入口、数据库变更、API 路由、部署配置、测试用例、验收记录。
- 核心业务流端到端闭环，不允许 stub、mock、硬编码成功、仅日志输出替代真实实现。
- UAT 报告必须基于真实运行验证、API/E2E/安全/性能/合规证据。

覆盖范围：Web、微信小程序、iOS、Android；9 个 Go 微服务；PostgreSQL、Redis、Kafka/Redis Streams、监控、告警、K8s/Helm、备份恢复；认证、账户、实名/KYB、订阅、支付、订单、退款、发票、积分、推荐返利、RFM、A/B、埋点、消息、推送、广告、运营后台、财务后台、RBAC、配置管理、审计合规；PIPL、等保、GB/T 25000.51、安全、性能、可观测性、灾备。

不得标记完成的情况：只有空壳页面、mock/硬编码成功、仅日志输出、只有 down migration、脚本无运行证据、页面不可达、接口未通过网关/部署路径暴露、外部依赖未配置却声称生产可用。

## 2. 100% 完成判定标准

每项需求必须通过 8 类门禁：

| 门禁 | 判定标准 |
|---|---|
| 需求一致性 | 覆盖 PRD 验收标准，不偏离 BRD 业务目标 |
| 后端实现 | handler/service/repository/model/权限/错误处理真实完整 |
| 端侧实现 | Web/小程序/iOS/Android 指定入口可达、可操作、状态完整 |
| 数据库 | 表、索引、约束、种子数据、up/down migration 完整 |
| API 与网关 | 路径、方法、字段、状态码一致，并经 api-gateway 暴露 |
| 部署配置 | Compose、Helm、环境变量、Secret、健康检查、监控完整 |
| 测试证据 | 单元、集成、API 合同、E2E、安全、性能、合规覆盖 |
| UAT 证据 | 有真实运行输出、日志、截图、trace、报告 |

需求状态枚举：完成、部分完成、Stub/Mock、缺失、外部依赖阻塞、不适用。

## 3. 86 项需求真实性追溯模型

建立“需求真实性追溯矩阵”，作为唯一事实源。每项 PRD 需求记录：PRD ID、验收标准、Phase、业务域、后端文件、端侧页面、API、DB migration、RBAC 权限点、部署配置、测试用例、验收证据、状态、缺口和阻塞项。

规则：
- 状态不能从文档继承，必须由证据链判定。
- 代码与 UAT 报告冲突时，以真实代码和运行验证为准。
- 修复后必须同步矩阵和 UAT 证据。
- 外部依赖必须拆分为“代码准备完成”和“外部资源未就绪”。

## 4. 当前关键缺口

第一轮只读审计发现的高风险缺口：

P0 阻断：仓库残留 exe/nul；新注册仍可能 SM3；payment-service 未完整接入 Compose/Gateway/Helm；订单/支付/退款/发票 migration 不完整；支付回调验签不足；推送 provider 多为日志 stub；注销审计和跨服务 PII 匿名化不足；限流不是 Redis 用户级差异化；安全头/TLS/HSTS/CSP 证据不足；审计日志不是哈希链；OTel 未全服务接入；备份恢复告警未闭环。

业务闭环：支付、订单、订阅、退款、发票未可信闭环；订阅购买未与支付成功强绑定；退款后积分/权益/审计不完整；推荐、收益、运营指标存在硬编码；RFM/A/B/埋点未生产级；财务后台和运营后台能力不足。

前端四端：RoleManagement 不可达；字段不一致风险仍存在；权限刷新恢复和页面级路由权限不足；订阅/积分/推荐/设备页成熟度不足；小程序支付与订阅消息闭环不足；iOS/Android 真实支付、推送、广告、生物识别、OAuth、离线、安全需重验。

外部依赖：支付商户与证书、发票平台、APNs/FCM/HMS/微信模板、短信通道、广告平台、K8s/TLS/镜像仓库、AlertManager webhook、第三方渗透、等保测评、PIA。

## 5. 业务闭环架构

采用“PRD Phase 顺序交付 + 业务闭环实施”。

交付顺序：Phase 6/P0 清零上线阻断；Phase 7/P1 补体验与增长；Phase 8/P2 补竞争力增强；Phase 9/P3 完成长期能力和最终验收。

业务闭环：
1. 认证、账户与合规：注册、登录、验证码、OAuth、生物识别、实名/KYB、密码哈希、注销、个人信息权利响应、PIPL。
2. 支付、订单、订阅、退款、发票：订单状态机、支付验签、订阅生效、升降级、续费、退款、对账、发票、财务后台。
3. 积分、推荐、返利与增长：积分流水、抵扣、邀请码、注册/付费转化、返利、K-factor、增长漏斗。
4. 数据产品、RFM、A/B 与埋点：统一埋点协议、事件持久化、RFM、漏斗、实验、Dashboard。
5. 消息、推送、移动端与广告：站内信、短信、邮件、APNs/FCM/HMS、微信订阅消息、设备 token、广告 SDK、频控、去广告升级。
6. 运营、财务、RBAC 与配置后台：用户、角色权限、实名审核、风控、黑名单、套餐、优惠券、促销、财务工作台、配置中心。
7. 安全、合规、可观测性与运维：限流、签名、防重放、安全头、TLS、审计哈希链、PII 脱敏、OTel、日志、指标、告警、K8s、备份恢复。

## 6. Phase 实施顺序

Phase 6/P0：真实性矩阵与仓库清理；argon2id 注册和验证码服务端校验；网关超时/504/Redis 用户级限流/安全头/签名防重放；注销跨服务匿名化和合规审计；payment-service 接入；订单/支付基础闭环；用户管理后台 P0；推送 provider 生产化或明确 sandbox；Helm、备份、健康检查、基础监控；P0 UAT 重跑。

Phase 7/P1：OAuth/一键登录；订阅购买、升降级、续费；积分抵扣和推荐返利；运营后台大屏；风控黑名单；移动端核心体验；小程序分享和订阅消息；集成测试与 E2E 扩展。

Phase 8/P2：电子发票；消息中心；RFM 与运营指标；A/B 实验；广告变现；FAQ/客服；移动端安全与性能；读写分离、KMS、服务发现、可观测性深度接入。

Phase 9/P3：长期数据产品能力；高级移动端能力；长期商业化能力；全量性能、安全、合规、UAT 最终验收；文档和报告归档。

## 7. 外部依赖处理

外部依赖采用“双状态”管理：代码完成度与外部资源就绪度分开标记。没有真实凭据时，代码必须支持 sandbox 与 production 两种模式，并在 UI、日志、健康检查和 UAT 中明确当前模式。生产完成不得依赖 mock success。

## 8. 测试与验收门禁

每个闭环必须至少通过：Go 单元测试、服务集成测试、API 合同测试、Web E2E、多角色 RBAC 测试、前后端字段一致性测试、异常路径测试、安全回归、性能抽检、合规检查。最终全量 UAT 使用五维模型：后端逻辑与代码、UI 全业务功能、性能、安全、合规。

## 9. 文档与报告修订策略

PRD、SSD、PLAN、UAT 报告、API 文档、部署文档必须随代码同步更新。现有 UAT 报告中与代码真实性冲突的结论需要降级或标记为待验证。最终报告只允许引用可复现证据。

## 10. 风险与降级原则

优先处理 P0 安全合规和商业闭环风险。外部依赖无法就绪时，只能标记为“代码已完成，外部资源未就绪”，不能标记产品 100% 生产完成。禁止为了通过验收保留硬编码成功、假 provider、假状态机或未接入页面。

## 11. 计划拆分与执行策略

由于本规格覆盖 86 项需求和多个独立子系统，实施计划不写成一个不可执行的巨型任务，而拆成一组可独立验收的计划。每个计划都必须产出可运行、可测试的软件增量。

计划顺序：
1. `phase6-p0-foundation`：清理仓库、建立真实性矩阵、修复注册密码哈希、接入 payment-service 部署路径、修复基础安全/健康/备份阻断项。
2. `phase6-payment-subscription`：订单、支付回调验签、订阅生效、退款、对账、发票基础闭环。
3. `phase6-account-compliance`：注销 Worker、跨服务 PII 匿名化、PIPL 权利响应、统一审计哈希链。
4. `phase7-growth-ops`：积分、推荐、返利、运营后台、风控、订阅体验和增长闭环。
5. `phase8-data-notification-mobile-ads`：RFM、A/B、埋点、消息、推送、移动端和广告能力。
6. `phase9-final-hardening-uat`：K8s、可观测性、安全、性能、合规、最终 UAT 与文档归档。

执行原则：先修阻断项，再补商业闭环；先建立自动验证，再修改生产代码；所有行为变更遵循 TDD；所有外部依赖用 sandbox/production 双模式显式标记；所有文档结论必须由运行证据支撑。
